### 1.2 Filtres SVG sur un élément HTML (`filter: url(#…)`) — verdict : à éviter en animation sur iOS

Faits documentés :

- **WebKit ne sait appliquer que des références locales** : `filter: url("#ref")` oui ; fichier SVG externe ou `data:` non. Bug 127102 (https://bugs.webkit.org/show_bug.cgi?id=127102, 2014) ; issue caniuse #3803 (https://github.com/Fyrd/caniuse/issues/3803, mise à jour 03/02/2025) ; comm. 9 du bug 261806 : « `url(data:image/svg+xml,...#id)` … never worked correctly in WebKit » (https://bugs.webkit.org/show_bug.cgi?id=261806, 09/10/2024) [P].
- **Coût CPU/rendu** : bug WebKit 287982 « Editor is slow because of an SVG filter » : un seul `filter: url(#grain)` sur un `::before` fait ramer le défilement dans WebKit, retiré = fluide ; confirmé sur Safari 26.0 le 09/10/2025 (https://bugs.webkit.org/show_bug.cgi?id=287982) [P]. Bug 263848 : « SVG animation is slow, as GPU is not used for filters » (statut NEW, https://bugs.webkit.org/show_bug.cgi?id=263848) [P].
- **Chromium** : le document de conception « Filter Effects » dit que le chemin GPU des filtres `url()` n'est déclenché que si l'élément est déjà dans une couche composée ; sinon CPU (https://www.chromium.org/developers/design-documents/image-filters/ — document ancien, date non indiquée, à lire comme historique) [P].
- **Smashing Magazine** (01/09/2021) [T] : « SVG Filters are still not optimized for performance … especially in WebKit and Firefox » ; WebKit applique des filtres complexes à du HTML mais **pas** avec `feImage` (l'élément disparaît), et un élément avec `position`/`transform` pouvait rester non filtré. https://www.smashingmagazine.com/2021/09/deep-dive-wonderful-world-svg-displacement-filtering/
- **GSAP, forum, 13/07/2022** [T] : `feTurbulence` + `feDisplacementMap` animés : « really sluggish » sur iOS, onglet Safari rechargé voire planté ; « SVG filters are pretty horrific for performance … animate them in very short bursts, or on a small area ». https://gsap.com/community/forums/topic/33075-gsap-and-feturbulence-mobile-performance/
- **Motion Components** [T, assertion non vérifiée par moi] : sous WebKit/iOS, un `filter: url()` sur du HTML « only repaints on scroll » ; ils filtrent donc du SVG. https://www.motion-components.dev/docs/text/motion-liquid/
- **liquid-glass** [T, dépôt avec tests Playwright WebKit] : `filter: url(#…)` fonctionne en WebKit pour déplacement + spéculaire, mais (a) WebKit a un « plafond de taille de source » au-delà duquel il abandonne les passes coûteuses (chroma + spéculaire) — donc pas de sur-échantillonnage ; (b) WebKit met en cache la sortie par `id` : il faut changer l'`id` du filtre à chaque changement de géométrie ; (c) un `feImage` qui change pendant un glissement fait « disparaître » le brillant. https://github.com/samasante/liquid-glass/blob/main/BROWSERS.md
- Safari ≥ 26 : correctifs de détail (`feMerge` mal positionné, etc.) dans les notes WebKit https://webkit.org/blog/17333/webkit-features-in-safari-26-0/ (15/09/2025) [P] — pas de mention d'une accélération des filtres `url()` sur HTML.

**Lecture** : le filtre SVG « creux + spéculaire » existe et rend bien, mais sur iOS il est CPU/Core-Image, sensible à la taille, avec des pièges de cache et de repaint. Le recalculer à chaque `pointermove` sur un sachet de ~320×480 px CSS (× DPR 3) est le scénario que tous les retours déconseillent. **Non vérifié** : le temps réel par frame sur un iPhone milieu de gamme (je n'ai aucun appareil).

### 1.3 Alternatives, de la plus sûre à la plus coûteuse

**A. Pile de dégradés CSS dont seul le `transform`/`opacity` bouge (recommandé)**
- Principe : ne jamais changer les *arrêts* d'un dégradé (repaint) ; déplacer des couches surdimensionnées par `transform: translate()`/`scale()` et `opacity`, propriétés que le thread de composition sait animer (https://web.dev/articles/animations-overview, mis à jour 06/10/2020 [P] : « changes to transforms and opacity can, in many cases, be handled by the compositor thread » ; si une animation déclenche paint ou layout, le thread principal travaille).
- Construction proposée (jugement, non éprouvée par moi) : (1) fond argent statique (dégradé linéaire froid) + **une texture de froissé pré-cuite** (petit WebP/PNG en niveaux de gris, ou canvas 2D dessiné une fois puis `toDataURL`/`ImageBitmap`) en `background-blend-mode`/`mix-blend-mode: soft-light` ; (2) une couche « reflet » = grand dégradé blanc-bleuté étroit, déplacée par `transform` avec un décalage de parallaxe selon la position du doigt ; (3) une couche « creux » = `radial-gradient` sombre→clair + `repeating-radial-gradient` très peu contrasté (plis concentriques), positionnée sous le doigt par `translate()`, amplitude par `scale()`/`opacity` selon la pression (détente au relâchement = animation de retour). Le « reflet qui se plie » s'obtient en deux couches de reflet à parallaxe opposée.
- Limite honnête : aucune de ces couches ne **déforme** l'étiquette ni les pointillés ; c'est de l'éclairage simulé, pas un relief géométrique.
- `mix-blend-mode` : Safari 8+, mais il force le mélange avec ce qui est dessous ; **et** il impose un aplatissement du contexte 3D (cf. §3). Le garder petit et jamais sur l'élément qui pivote.

**B. Canvas 2D** : un petit `<canvas>` (taille du sachet, DPR plafonné à 2) où l'on peint à chaque frame des dégradés radiaux (`createRadialGradient`) pour le creux et le reflet. Peindre des dégradés est peu coûteux ; un éclairage **par pixel** (`getImageData`, normale + Phong en JS) sur ~135 000 px/frame est lourd pour un milieu de gamme — **jugement, non mesuré**. Piège iOS : limites de canevas (zone max 16 777 216 px avant iOS 18, 67 108 864 px mesurés à partir de iOS 18.0 ; mémoire totale 384 Mo citée) et non-libération rapide — mettre `width = height = 0` pour libérer. Sources : https://pqina.nl/blog/canvas-area-exceeds-the-maximum-limit/ , https://lionpuro.com/posts/canvas-is-finally-usable-on-safari/ (10/05/2025) [T] ; https://bugs.webkit.org/show_bug.cgi?id=271002 (limite 8192×8192 demandée, 14/03/2024) , https://bugs.webkit.org/show_bug.cgi?id=195325 (échec « Total canvas memory use exceeds … » ; ouvert comme comportement attendu, contournement `width=0`) [P]. Une carte de combat ayant déjà deux canevas, ajouter un troisième n'est pas gratuit.

**C. WebGL (WebGL2, shader maison sans dépendance)** : un quad, un fragment shader qui calcule une hauteur (gaussienne sous le doigt + ondes concentriques + bruit fixe), en déduit la normale et un éclairage à environnement dégradé froid. C'est la seule voie qui donne un vrai « creux lisse + plis concentriques + reflet spéculaire qui se plie ». Coût : GPU modeste (un quad) ; WebGL2 existe sur Safari 15+ et Chrome 56+ (BCD). Pièges : perte de contexte, jsdom sans WebGL (il faut un repli statique pour les tests), mémoire iOS. Références open source de shaders de feuille/holo : Holosticker (three.js, PBR holofoil, https://github.com/jal-co/holosticker), Pokebox (GLSL, https://github.com/selop/pokebox) — **lourds** (three.js) ; l'idée seule est réutilisable. **Non vérifié** : tenue de 60 im/s sur milieu de gamme.

**D. API Houdini Paint** : **exclue** — Chrome/Edge seulement, Safari iOS non supporté jusqu'à 27.2 (caniuse). Ne servirait que d'amélioration progressive Chrome.

**E. `@property`** : permet d'animer une variable typée (`--press`, `--x`) et de la lire dans plusieurs dégradés ; support complet (Chrome 85, Safari 16.4). **Piège (jugement, non vérifié par une source)** : changer une variable CSS invalide le style et le paint de l'élément et de ses descendants, donc c'est du travail sur le thread principal à chaque frame, comme n'importe quel changement de dégradé. À réserver aux petites surfaces.

### 1.4 Ce qu'on peut raisonnablement attendre
- **A** : un film argent crédible au repos et au toucher (reflet froid qui glisse, creux sombre, anneaux), sans vraie déformation. Fluide parce que presque tout passe par `transform`/`opacity`.
- **C** : le rendu le plus proche du film froissé, au prix d'un canevas WebGL et d'un repli.
- **Filtres SVG** : rendu superbe sur Chrome, risqué sur iOS ; ne pas en dépendre.

## 2. Déchirure progressive qui suit le pointeur

### 2.1 Options et compat
- **`clip-path: polygon()`** sur HTML : Safari 7+, animable (`@keyframes`) Safari 12.1+ (BCD `css/properties/clip-path.json`, sous-clés `html_elements`, `basic_shape`, `is_animatable`) [P]. L'interpolation de deux `polygon()` exige le même nombre de sommets (https://drafts.csswg.org/css-shapes/#basic-shape-interpolation, cité dans le fil paint-dev ci-dessous) [P]. Ici on ne l'anime pas : on **écrit** le polygone à chaque `pointermove`.
- **`clip-path: path()`** : Safari 13.1 (préfixé 10), coordonnées absolues en px (pas de pourcentage) [P BCD].
- **`mask-image`** : Chrome 120 sans préfixe, Safari 15.4 (BCD `css/properties/mask-image.json`) [P] ; un masque dentelé demande une image pré-cuite ; un masque dégradé ne donne qu'un bord droit.
- **Canvas / SVG path** : possibles mais ils sortent l'élément du DOM stylé (le sachet est du HTML/CSS) ; `<clipPath>` SVG référencé en `clip-path: url(#id)` — **non vérifié** côté Safari.

### 2.2 Coût
- Dans Chrome, `clip-path` n'est pas un déclencheur de composition direct ; il est dessiné au paint, et un changement de forme redessine (fil paint-dev « Moving clip-path to the compositor », 2017, https://groups.google.com/a/chromium.org/g/paint-dev/c/3bXUo0X3C5I) [P, ancien]. Chrome a ensuite livré des animations `clip-path` **composées** (`CompositeClipPathAnimations`, commits 2021→2024, ex. https://github.com/chromium/chromium/commit/85703f3fc5cf6efe742267e73c2a5f67b87da0f4, 17/10/2024 ; annonce https://developer.chrome.com/blog/hardware-accelerated-animations, 22/02/2021) [P] — mais cela concerne les animations **déclaratives** (CSS/WAAPI), **pas** un style réécrit en JS à chaque événement. Notre déchirure suit le doigt : c'est donc du repaint par frame sur le thread principal. Sur ~320×120 px et 25–60 sommets le coût est probablement faible — **jugement, non mesuré**.

### 2.3 Construction proposée (pas de dépendance)
1. Précalculer **une seule fois** la ligne dentelée `y[i]` (marche aléatoire lissée, graine fixe pour que les tests et les planches soient identiques). Même procédé que la démo « Holo Pack Opening » : polygone de 25 points « from a smoothed random walk », appliqué aux deux moitiés (https://effect-labs.com/en/effects/cards/holo-pack-opening.html, mise à jour 04/10/2026 ; code payant — on ne copie que l'idée) [T].
2. Deux couches affichant la **même face** du sachet : le **corps** (clip : sous la ligne dentelée pour x ≤ p·W, sous la ligne droite au-delà) et la **bande du haut** (clip complémentaire). Un seul tableau `y[]` alimente les deux : pas de jour ni de recouvrement entre elles.
3. Le moteur d'état donne `p ∈ [0,1]` ; n'écrire le style que si `p` a changé d'au moins ~1 px (quantifier).
4. **Détachement** (à `p = 1` ou au relâchement au-delà du seuil) : animer la bande avec **WAAPI** (`element.animate()`, Safari 13.1 ; BCD `api/Element.json`) sur `transform` + `opacity` seulement — cela passe par le compositeur. `will-change: transform` posé au début du détachement puis retiré, comme le recommande MDN : « last resort », à activer/désactiver par script autour du changement, pas en feuille de style (https://developer.mozilla.org/en-US/docs/Web/CSS/will-change, lu via `mdn/content`, dernière modif. non relevée) [P]. Une fois `finished`, retirer la bande du DOM.
5. **Annulation** : `p` suit le doigt dans les deux sens ; au relâchement avant la fin, animer `p` vers 0 (spring/ease). Avec Motion déjà installé : `animate(motionValue, 0)` ; la valeur Motion met à jour le DOM **sans re-rendu React** (« Changes to the motion value will update the DOM without triggering a React re-render », https://motion.dev/docs/react-motion-value, via Context7) [P].
6. Projeter la position du doigt sur l'axe des pointillés : `p = clamp((x − x0)/(W − x0))`, avec une tolérance verticale (« tube ») au-delà de laquelle on annule — choix de conception, pas une norme.

Référence de seuil dans une démo : `pct = dx / (strip.offsetWidth * 0.62)`, fin à `pct ≥ 1`, retour animé 0,3 s au relâchement, `pointercancel` traité comme un relâchement (https://github.com/alechash/unsleeved, `index.html` lignes ~1560-1590, lu le 28/10/2026 ; **sans licence** → référence de lecture seulement) [T].

## 3. Retournement 3D de cartes

### 3.1 Compat et règles
- `backface-visibility` : Safari 15.4 sans préfixe (préfixé 5.1) ; Chrome sans préfixe (BCD `css/properties/backface-visibility.json`) [P].
- `transform-style: preserve-3d` : Safari 9 ; avant Safari 17, `::before`/`::after` étaient **hors** du contexte 3D (bug 256430) (BCD `css/properties/transform-style.json`) [P].
- `perspective` : sur iOS 13 elle « did not function properly », corrigé en iOS 14 (BCD `css/properties/perspective.json`) [P].
- **Aplatissement** : la spécification liste les valeurs qui forcent `transform-style` à `flat` (donc cassent la 3D des descendants) : `overflow` ≠ `visible`/`clip`, `opacity < 1`, `filter` ≠ `none`, `clip-path` ≠ `none`, `mask-image` ≠ `none`, `mix-blend-mode` ≠ `normal`, `isolation: isolate`, `contain: paint` (donc aussi `content-visibility: hidden`). https://www.w3.org/TR/css-transforms-2/ (lu le 28/10/2026) [P]. **Règle pour le projet** : aucun de ces réglages sur le nœud qui porte `preserve-3d` ni sur ses ancêtres jusqu'à la `perspective`. Les VRAIS composants de carte (probablement `overflow: hidden` + `border-radius`) doivent vivre **à l'intérieur** d'une face, jamais sur le conteneur 3D.

### 3.2 Pièges Safari/iOS documentés
- Safari n'applique pas le clip `overflow: hidden` + `border-radius` d'une carte à un enfant composé (`mix-blend-mode: screen`) quand la carte a aussi `preserve-3d` ; le reflet déborde des coins ; correctif : `border-radius: inherit` sur l'enfant (PR https://github.com/Jakubantalik/transitions.dev/pull/3) [T].
- `border-radius` + `overflow: hidden` + enfant transformé : bug Safari ancien ; contournements `z-index`, `transform: translateZ(0)`, `mask-image`, `will-change` (https://gist.github.com/domske/b66047671c780a238b51c51ffde8d3a0, 09/03/2021, testé iOS 14.4) [T].
- Clignotements de faces avec `backface-visibility: hidden` sur iOS (2020-2023, Stack Overflow) : questions non résolues de façon uniforme, pas de bug moteur identifié [T] — **traiter comme un risque, pas un fait**. Un bug WebKit « 263255 » (faces semi-transparentes qui « se dissolvent ») a été **corrigé** le 14/11/2024 (https://www2.webkit.org/show_bug.cgi?id=263255) [P], reproduit sur Epiphany, pas sur Safari.

### 3.3 Technique la plus sûre : retournement en deux phases (sans `preserve-3d` ni `backface-visibility`)
Animer le dos de `rotateY(0 → 90°)` puis, à 90° (la carte est un trait), échanger `visibility`/`opacity` et animer la face de `rotateY(−90° → 0)`. Une seule `perspective` sur le parent (ou `perspective()` dans la fonction `transform`). Cette variante est évoquée comme contournement dans https://stackoverflow.com/questions/20389553 (variante `scaleX(-1)`) [T]. Avantages : aucun aplatissement à surveiller, aucune dépendance à `backface-visibility`. Inconvénient : le « mi-parcours » n'a pas l'épaisseur d'un vrai pivot (négligeable sur une carte).

Si l'on garde le retournement classique (une carte = `.flip` en `preserve-3d` + deux faces en `backface-visibility: hidden`) : tester sur iPhone réel, poser `-webkit-backface-visibility` n'est plus nécessaire d'après BCD pour Safari ≥ 15.4 (**le plancher iOS du projet n'est pas dans ce que j'ai lu — non vérifié**).

### 3.4 Coût de composition pour cinq cartes
- Une couche composée coûte de la mémoire de texture et de la bande passante CPU→GPU (https://web.dev/articles/stick-to-compositor-only-properties-and-manage-layer-count, lu le 28/10/2026) [P].
- Ordre de grandeur (**calcul à partir de la formule texture = largeur × hauteur × DPR² × 4 octets**, hypothèses de moi : carte 160×224 px CSS, DPR 3) : ≈ 480×672×4 ≈ 1,3 Mo par carte → ≈ 6,5 Mo pour cinq. Une couche plein écran 390×844 à DPR 3 pèse ≈ 11,9 Mo : **ne jamais empiler plusieurs voiles plein écran** (éclat, poussière, assombrissement). Hypothèses à confirmer sur appareil.
- Promouvoir (par `transform` animé ou `will-change`) seulement pendant l'animation, relâcher après.

## 4. Éclat + poussière

- **Éclat doré** : un seul élément `radial-gradient` (or → transparent) animé en `opacity` + `transform: scale()` (compositeur). Éviter `mix-blend-mode: screen` plein écran (lecture de l'arrière-plan à chaque frame, force aussi l'aplatissement 3D ; cf. §3.1) ; un dégradé alpha doré simple suffit. `filter` animé : Chrome l'accélère par défaut avec `opacity` et `transform` (https://developer.chrome.com/blog/hardware-accelerated-animations, 22/02/2021) [P] ; côté WebKit, l'accélération des filtres CSS « Currently Mac only, using CoreImage … Animation is done in software » figure dans un ancien changement WebKit (https://trac.webkit.org/changeset/103148/webkit, date non indiquée dans l'extrait lu, ancien) [P] — **état actuel sur iOS : non vérifié**. À éviter : `blur()` animé sur de grandes surfaces.
- **Poussière** : canevas 2D, le projet en fait déjà (deux canevas, ≤ 600 particules). Conseils sourcés : plafonner le DPR du canevas (limites iOS ci-dessus, §1.3 B), ne pas créer/détruire des canevas à répétition (bug WebKit 195325), arrêter la boucle `requestAnimationFrame` quand plus rien ne vit.
- **CSS seul** : la démo « Holo Pack Opening » utilise 9 étincelles + 3 traînées créées en JS avec des variables CSS aléatoires (`--tx/--ty/--d/--s`), 17 `@keyframes`, 23 Ko de CSS + 8 Ko de JS, sans dépendance (https://effect-labs.com/en/effects/cards/holo-pack-opening.html, 04/10/2026) [T]. Cela montre que quelques dizaines d'éléments DOM animés par `transform`/`opacity` tiennent ; au-delà, passer au canevas relève de mon **jugement** (pas de seuil sourcé).
- **60 im/s sur milieu de gamme** : aucune source ne le garantit ; il faut mesurer sur appareil (§7). DevTools reconnaît qu'il « can't truly simulate the CPUs of mobile devices » (https://developer.chrome.com/docs/devtools/performance/reference, lu le 28/10/2026) [P].

## 5. Gestes (Pointer Events)

### 5.1 Compat
- Pointer Events : Chrome 55, Safari 13 ; `setPointerCapture` : Chrome 55, Safari 13 ; `touch-action` : Chrome 36, Safari 13 (iOS 9.3) ; `getCoalescedEvents` : Chrome 58, **Safari 18.2** ; `getPredictedEvents` : Chrome 77, Safari 18.2 (BCD `api/PointerEvent.json`, `api/Element.json`, `css/properties/touch-action.json`) [P].

### 5.2 Règles sourcées
- `touch-action` : « An application using Pointer events will receive a `pointercancel` event when the browser starts handling a touch gesture » (pan/zoom) ; le navigateur **intersecte** les valeurs de l'élément touché et de ses ancêtres jusqu'au conteneur défilant ; à poser **avant** le geste (https://developer.mozilla.org/en-US/docs/Web/CSS/touch-action, via `mdn/content`) [P]. `touch-action: none` = pas de défilement/zoom natif à partir de l'élément (https://www.w3.org/TR/pointerevents/) [P].
- `pointercancel` : le navigateur « MUST fire » `pointercancel` quand il détecte un scénario de suppression du flux ; l'événement **n'est pas annulable** (`cancelable = false`) (https://www.w3.org/TR/pointerevents/, §3.3) [P]. **Traiter `pointercancel` et `lostpointercapture` exactement comme un relâchement-annulation** (retour de l'étiquette, p → 0, creux qui se détend).
- Capture : `setPointerCapture(e.pointerId)` dans `pointerdown` redirige les événements suivants vers l'élément même si le doigt sort ; le dépôt `unsleeved` le fait (ligne ~1568) ; la spec décrit aussi une capture **implicite** et son relâchement implicite (table des matières de https://www.w3.org/TR/pointerevents/ ; détail non relu) [P/T].
- **Multi-touch** : ne suivre qu'un `pointerId` (le premier, `isPrimary`) ; ignorer les autres ; si un second doigt arrive, annuler proprement ou l'ignorer (choix de conception, non normatif). `isPrimary` est défini par la spec ; page non relue en détail — « non vérifié ici ».
- **Défilement qui vole le geste** : couvert par `touch-action` ci-dessus ; sur Android Chrome, le *pull-to-refresh* est une autre cause : le désactiver par `overscroll-behavior-y: contain` sur l'écran concerné (https://developer.chrome.com/blog/overscroll-behavior — « disabling the pull-to-refresh feature on mobile ») [P]. `overscroll-behavior` n'est que **partiel** sur Safari 16 (« no effect on scroll containers that have no scrollable overflow », BCD) [P].
- **Écouteurs passifs** : inutile de se battre avec `preventDefault` en `touchmove` si l'on reste en Pointer Events + `touch-action: none` ; je n'ai **pas** relu la doc des écouteurs passifs par défaut de Chrome — non vérifié.
- **iOS** : pour éviter sélection/loupe au maintien du doigt, `-webkit-user-select: none` (BCD : Safari n'a que le préfixe stable, `user-select` sans préfixe seulement en « preview ») ; `-webkit-touch-callout: none` non relu — non vérifié.
- **Précision** : `getCoalescedEvents()` (Safari 18.2+, Chrome 58+) renvoie les points intermédiaires entre deux `pointermove` ; utile pour que la déchirure ne saute pas de points ; facultatif.

### 5.3 Seuils usuels
- Aucune valeur normative web. Android expose `ViewConfiguration.getScaledTouchSlop()` : « distance a touch can wander before we think the user is scrolling » (https://developer.android.com/reference/android/view/ViewConfiguration ; la valeur en dp n'apparaît pas dans l'extrait lu — **non vérifié**, mon souvenir est 8 dp). iOS : pas de valeur documentée relue — non vérifié.
- Démo lue : fin de déchirure quand le doigt a parcouru 62 % de la largeur de la bande, retour animé sinon (`unsleeved`, [T]). Pour le projet : seuil d'**étiquette** et de **déchirure** à poser en tests de jeu (suggestion : 8-10 px de « slop » avant d'engager le glissement, étiquette détachée vers 50-60 % d'une course, tolérance verticale d'environ 40 px — **tous jugements, à régler sur appareil**).

### 5.4 Accessibilité (obligatoire de l'avoir en tête)
- WCAG 2.2 SC 2.5.1 (niveau A) : toute fonction par geste à trajectoire (path-based) doit être utilisable **avec un seul pointeur sans geste à trajectoire**, sauf si la trajectoire est essentielle (https://www.w3.org/WAI/WCAG22/Understanding/pointer-gestures.html) [P]. SC 2.5.7 (niveau AA) : toute fonction par glisser doit pouvoir se faire **sans glisser** (https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html) [P]. Le glissement le long des pointillés est exactement ce cas : prévoir un **bouton « Ouvrir »** (et clavier) qui déclenche l'état final ; le geste « tout afficher » du cahier des charges peut jouer ce rôle s'il est un simple appui.

## 6. Retour sensoriel

### 6.1 Vibration
- `navigator.vibrate` : Chrome 32 (Android), **exige une activation utilisateur depuis Chrome 60** (sinon renvoie `false`) ; **Safari/iOS : non supporté** ; Firefox Android : désactivé (renvoie `true` sans vibrer depuis la 79) (BCD `api/Navigator.json`, https://developer.mozilla.org/en-US/docs/Web/API/Navigator/vibrate, modif. 30/11/2025) [P]. MDN : certains appareils ne vibrent pas en mode silencieux / ne pas déranger [P].
- Position de WebKit : « WebKit remain firmly against this API » (commentaire d'un membre de l'équipe, 08/10/2024, https://github.com/web-platform-tests/interop/issues/718) ; proposition non retenue pour Interop 2025 (13/02/2025) [P/T].
- **Contournement iOS non officiel** : retour haptique d'un `<input type="checkbox" switch>` (Safari 17.4 pour `switch`, haptique depuis iOS 18, bug WebKit 266066, https://bugs.webkit.org/show_bug.cgi?id=266066 ; PR 38473 « should require user activation », 03/01/2025) [P]. Une bibliothèque tierce l'exploite (https://github.com/tijnjh/ios-haptics) ; un banc d'essai de juin 2025+ affirme que **depuis iOS 26.5 les haptiques déclenchés par script ont été retirés** : seul un vrai appui sur un vrai interrupteur fonctionne (https://sergey-grishchev.github.io/haptics-playground/) [T, non vérifié par moi]. **Conclusion** : sur iOS, pas de haptique piloté par le jeu ; sur Android Chrome, `vibrate([15])`-type possible sur geste. Prévoir un réglage, garder `if ('vibrate' in navigator)`, ne jamais en faire une information indispensable.

### 6.2 Audio : Web Audio contre `HTMLAudioElement`
- **Recommandation pour un son court déclenché sur geste** : Web Audio, tampon décodé d'avance, `AudioBufferSourceNode.start()`. MDN : « the latter [fetch + decode into a buffer] when working with shorter, more sample-like tracks … more control » (https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Best_practices) [P]. Les `HTMLMediaElement` sont asynchrones par nature (de `play()` à `currentTime`) (Stack Overflow, 02/2019, auteur Kaiido) [T]. Mesure d'un développeur : `new Audio().play()` crée l'élément, récupère l'URL, décode, puis joue — tout après l'appui ; avec tampons Web Audio préchauffés, appui → lecture ≈ 1,8 ms (https://fadongkwon.com/posts/audio-latency-ios/, 15/09/2026) [T, mesure unique, un appareil].
- **Latence de sortie** : « very very low on OSX and iOS (a few milliseconds) … Android … between 12.5ms … and 150ms on some very cheap devices » (https://padenot.github.io/web-audio-perf/, auteur : ingénieur audio de Mozilla ; date non relevée, ancien) [T/P]. `AudioContext.outputLatency` existe sur Safari 18.4+ / Chrome 102+, `baseLatency` Safari 14.1+ / Chrome 58+ (BCD `api/AudioContext.json`) — utile pour diagnostiquer, pas pour compenser.
- **Déblocage (iOS surtout)** :
  - La spec HTML définit les événements **déclencheurs d'activation** : `keydown` (hors Échap), `mousedown`, **`pointerdown` seulement si `pointerType` est `mouse`**, **`pointerup` si `pointerType` n'est pas `mouse`**, `touchend` (https://html.spec.whatwg.org/multipage/interaction.html, lu le 28/10/2026) [P]. **Donc au doigt, `pointerdown` ne débloque pas l'audio ; `pointerup`/`touchend`/`click` oui.** Un `touchstart` ne le fait plus depuis Safari 9 (bug WebKit 149367 ; commentaire d'un ingénieur WebKit : « "touchend" is the correct event … the first explicit user gesture will lift the audio restriction for an entire AudioSession. So, after the first user gesture, audio initiated by "touchstart" events will be audible », 29/09/2015, https://bugs.webkit.org/show_bug.cgi?id=149367) [P].
  - BCD, `AudioContext()` (Safari 14.1) : « New audio contexts are suspended until `resume()` is called via user action » [P]. MDN : « Create or resume context from inside a user gesture » [P].
  - **Recette** : créer **tardivement** le `AudioContext` (pas au chargement), appeler `ctx.resume()` dans le **premier `pointerup`/`click`** de la session (un écouteur global « une fois », ou le clic qui mène à l'écran d'ouverture), décoder les deux tampons à ce moment-là ; ensuite `source.start()` marche depuis n'importe quel code, y compris au milieu d'un glissement. Gérer l'état `interrupted` propre à Safari (écran verrouillé, changement d'app) : relancer `resume()` au prochain geste (code de `pixijs/sound`, https://github.com/pixijs/sound/blob/main/src/webaudio/WebAudioContext.ts) [T].
  - Un déblocage échoue si le doigt reste trop longtemps (c'est alors un défilement) : bug WebKit 248265 (https://bugs.webkit.org/show_bug.cgi?id=248265, 23/11/2022) [P].
- **Interrupteur silencieux iPhone** : Web Audio est traité comme « ambient » : il **obéit** à l'interrupteur, alors que `<audio>` l'ignore (WebKit 237322, 252746) ; réponse d'un ingénieur WebKit : « Since iOS 17, you can set the audio session type to "playback" … By default the type is `ambient` » (https://bugs.webkit.org/show_bug.cgi?id=237322, 25/09/2024) ; `Navigator.audioSession` : Safari 16.4, **absent de Chrome** (BCD) [P]. `playback` interrompt la musique de l'utilisateur ; la spec décrit `transient` comme « Transient audio, such as a notification ping … on top of playback audio » (cité dans https://nattog.dev/blog/web-audio-ios-unmute, 22/11/2025) [T]. **Décision à prendre par le projet** (non tranchée ici) : respecter l'interrupteur (comportement par défaut) ou `transient`.
- **Formats** (caniuse, lu le 28/10/2026, support dans l'élément `audio`, pas forcément dans `decodeAudioData`) : **MP3 : iOS ≥ 8** ; **AAC : iOS ≥ 8** ; **Opus : support complet seulement à partir d'iOS 18.4**, auparavant seulement dans un conteneur CAF (débit constant) ou WebM avec régression connue (notes de https://raw.githubusercontent.com/Fyrd/caniuse/main/features-json/opus.json) [P/T]. OGG Vorbis : **non vérifié** pour iOS. Pour l'alpha : **MP3 ou AAC (m4a)**, mono. Poids : un son d'1,5 s à 128 kb/s ≈ 24 Ko (calcul : 16 Ko/s) ; décodé en flottants 32 bits stéréo 44,1 kHz ≈ 529 Ko en mémoire (calcul) : négligeable. Le piège mémoire de Web Audio ne concerne que les longs morceaux (« a 5Mb mp3 … 55Mb » décodé, https://medium.com/@Rich_Harris/phonograph-js-tolerable-mobile-web-audio-55286bd5e567, 11/08/2016) [T].
- **Déclencher sans retard sur un appui** : tampons décodés d'avance ; contexte déjà `running` ; aucun `new Audio()` à l'appui ; pas de `await` avant `start()`. Si le contexte est encore `suspended` à l'appui, ne **pas** attendre : sauter le son plutôt que le jouer en retard (choix de conception).
- Licence libre sourcée : **hors périmètre de cette note** (non traité).

## 7. Performance et entretien

- **Compositeur** : `transform` et `opacity` en priorité (https://web.dev/articles/animations-overview, 06/10/2020) ; Chrome accélère par défaut `opacity`, `filter`, `transform`, et a ajouté `background-color`/`clip-path` pour les animations déclaratives (https://developer.chrome.com/blog/hardware-accelerated-animations, 22/02/2021) [P]. `clip-path` réécrit par script n'en profite pas (§2.2).
- **Couches** : chacune coûte mémoire GPU et transfert (https://web.dev/articles/stick-to-compositor-only-properties-and-manage-layer-count) ; mesurer avec le profileur de peinture [P].
- **`will-change`** : dernier recours, ne pas l'appliquer à beaucoup d'éléments ni en permanence, l'activer/désactiver par script avant/après (MDN) [P]. Safari 9.1+, Chrome 36+ (BCD).
- **`content-visibility`** : Chrome 85, Safari 18 (BCD) ; sans intérêt pour cinq cartes visibles ; utile pour des listes hors écran. Un sous-arbre `hidden` n'a pas de géométrie utilisable (correctif Safari 26 : « Fixed geometry values inside `content-visibility: hidden` subtrees », https://webkit.org/blog/17333/webkit-features-in-safari-26-0/) [P] : **ne jamais mesurer** un élément qu'on y a placé.
- **Ce qui fait ramer (sourcé)** : filtres SVG sur HTML (§1.2), grandes surfaces filtrées/floutées, couches nombreuses/grandes, canevas trop grands sur iOS (§1.3 B), re-rendus React à chaque événement. Pour ce dernier : écrire dans des `MotionValue` ou des refs (Motion : « `motion` components bypass React's render cycle », « Using motion values instead of React state … will avoid re-renders », https://motion.dev/docs/react-motion-component) [P].
- **Mesure** : DevTools Performance avec ralentissement CPU (calibrable), en rappelant que ce n'est qu'une approximation (https://developer.chrome.com/docs/devtools/performance/reference) ; débogage à distance sur un vrai téléphone ; `PerformanceObserver` existe partout (Safari 11) mais `long-animation-frame` (`PerformanceLongAnimationFrameTiming`) est **Chrome seulement** (BCD : Safari `false`, « experimental ») [P]. Outil maison facile (jugement) : échantillonneur de `requestAnimationFrame` (histogramme des deltas) activé en dev. Inspecteur Web de Safari sur iPhone : **non vérifié** (pas de doc Apple relue).
- **Geler / sauter une animation proprement** :
  1. Faire de l'état visuel une **fonction pure** de `(phase, progress)` ; « tout afficher » = passer la machine en phase finale, rendre sans transition (attribut local `data-instantane` qui met `transition-duration/animation-duration: 0s`) — plutôt que de tuer des minuteries une à une.
  2. Pour les animations WAAPI : `animation.finish()` (Chrome 75, Safari 13.1), `cancel()`, `commitStyles()` (Chrome 84, Safari 13.1) (BCD `api/Animation.json`) ; `element.getAnimations()` (Chrome 84, Safari 13.1) pour toutes les saisir. Avec Motion : `controls.complete()` « Immediately completes the animation, running it to the end state » (https://motion.dev/docs/animate) [P].
  3. Canevas : annuler `requestAnimationFrame`, vider le canevas, ne plus écrire.
  4. Réutiliser le point de bascule existant (`useMouvementReduit`, `src/components/use-mouvement-reduit.ts` : réglage du store **ou** `prefers-reduced-motion`) : sous « Mouvement réduit », afficher directement l'état final et les cinq cartes à plat. `MotionConfig reducedMotion="user"` de Motion ne coupe que les animations de transformation/mise en page (https://motion.dev/docs/react-accessibility) : **insuffisant** ici, d'où le point de bascule du projet.

## 8. Testabilité

### 8.1 jsdom : machine d'états pure + horloge injectée
- **Cœur** : un réducteur pur `etape(état, événement, maintenant) → état'` où l'événement est `{type:'down'|'move'|'up'|'cancel', x, y, id, t}` normalisé, la **géométrie** (largeur, ligne de déchirure, seuils) est passée en paramètre (jsdom ne calcule pas la mise en page : `getBoundingClientRect` renvoie des zéros — comportement général de jsdom, non re-relu ici). Les temps (détente, retour, cascade des cartes) sont des transitions de phase déclenchées par `maintenant`, jamais par `setTimeout` caché. Les tests appellent le réducteur avec des séquences de points : seuil d'étiquette atteint/non atteint, `p` monotone, annulation par `cancel`, saut « tout afficher » depuis chaque phase, idempotence, second doigt ignoré.
- **Test de composant** : jsdom installé dans le projet contient bien `PointerEvent` (fichier `node_modules/jsdom/lib/jsdom/living/events/PointerEvent-impl.js` présent) mais **aucune** implémentation de `setPointerCapture`/`releasePointerCapture`/`hasPointerCapture` (recherche dans `node_modules/jsdom/lib/jsdom/living` : 0 occurrence) et **ni `Element.animate` ni `getAnimations`** (idem : 0 occurrence). `src/test/setup-jsdom.ts` ne définit actuellement que `matchMedia`. Il faudra des **stubs** dans le setup : `Element.prototype.setPointerCapture = () => {}` etc., `Element.prototype.animate` renvoyant un objet `{finished: Promise, finish(), cancel()}`, `HTMLCanvasElement.prototype.getContext` (jsdom sans paquet `canvas` renvoie `null`), et un `AudioContext` factice. Vérifier alors que le **composant** relaie bien les événements au réducteur, et que `pointercancel` revient à l'état initial.
- **Horloge** : Vitest, `vi.useFakeTimers()` : l'option `toFake` par défaut couvre « everything available globally except `nextTick` and `queueMicrotask` », donc aussi `requestAnimationFrame` et `performance` (doc `main` : https://github.com/vitest-dev/vitest/blob/main/docs/config/faketimers.md, lue le 28/10/2026 — **vérifier que la version de Vitest installée a le même défaut**) [P]. Ne pas dépendre de cet automatisme : injecter une fonction `maintenant()`.
- **Garde-fou « le contrôle mord »** (règle du projet) : un test qui alimente le réducteur avec un cas fautif (p qui recule sans annulation, étiquette détachée sous le seuil) et vérifie que l'assertion échoue.

### 8.2 Prouver par planche de frames dans Chrome
- Le script existant `scripts/filmer-animation.mjs` photographie une zone **toutes les N ms réelles**, légende l'instant **mesuré** (une capture prend quelques dizaines de ms), fige l'horloge de la page (`--horloge`, `page.clock.setFixedTime`), force `reducedMotion: 'no-preference'` et amorce le store avec `reducedMotion: false` (lu dans le fichier le 28/10/2026). Il sait **cliquer**, pas **glisser**.
- Pour une animation **pilotée au pointeur**, la bonne abscisse de la planche est la **progression**, pas le temps : une case par `p ∈ {0, .1, …, 1}`. Deux moyens :
  1. **Geste réel en Chromium** : Playwright `page.touchscreen` « is limited to emulating tap gestures » (https://github.com/microsoft/playwright/blob/main/docs/src/api/class-touchscreen.md) ; pour du tactile à plusieurs étapes, ouvrir une session CDP et appeler `Input.dispatchTouchEvent` (« Dispatches a touch event to the page », https://github.com/ChromeDevTools/devtools-protocol/blob/master/json/browser_protocol.json) [P] — ce chemin déclenche de **vrais** `pointer*` de type `touch` et exerce `touch-action`/`pointercancel`, alors que `page.mouse` produit des événements `pointerType: 'mouse'` (jugement). Playwright documente aussi l'émulation de `touchstart/touchmove/touchend` par `dispatchEvent`, mais sans `isTrusted` (https://github.com/microsoft/playwright/blob/main/docs/src/touch-events.md) [P] — insuffisant pour nos Pointer Events.
  2. **Crochet de développement** : exposer en dev seulement `window.__paquet.allerA({phase, p})` qui pilote la machine ; plus déterministe, mais ne prouve pas le câblage des gestes (à compléter par le moyen 1 pour un seul passage complet).
- **Temps déclaratif** (cascade des cartes, retournement, éclat) : `page.clock.runFor(ms)` simule `Date`, `requestAnimationFrame`, minuteries (https://github.com/microsoft/playwright/blob/main/docs/src/clock.md) ; mais les animations CSS/WAAPI suivent la **chronologie du document**, pas ces horloges simulées — **non vérifié**. Pour elles : `document.getAnimations().forEach(a => { a.pause(); a.currentTime = t })` (WAAPI, Safari 13.1/Chrome 84), ou CDP `Animation.seekAnimations` / `Animation.setPlaybackRate` (« Sets the playback rate of the document timeline ») (même fichier de protocole) [P].
- **Stress milieu de gamme** : CDP `Emulation.setCPUThrottlingRate` (« Enables CPU throttling to emulate slow CPUs ») [P] ; indicatif seulement.
- **Limite à écrire dans le rapport** : Playwright-WebKit ≈ Safari (annoncé « WebKit ≈ Safari » par liquid-glass [T]), mais **pas iOS** : le rendu 3D/filtre/audio sur iPhone ne se prouve que sur appareil réel — **non prouvable ici**.

Tout afficher** | État visuel = fonction pure `(phase, progress)` ; le geste passe la machine en phase finale, rendu **sans transition** (`data-instantane`) ; annulation des WAAPI (`finish()`/`cancel()`), de la boucle canevas, des minuteries ; même bascule que « Mouvement réduit ». | Éléments laissés en route (minuteries, animations WAAPI, canevas) qui s'exécutent après le saut. | Le geste exact de saut (appui long ? bouton ?) n'est pas défini par le cahier des charges. |

### Ce qui reste incertain (global)
1. **Aucune mesure** (ni Chrome, ni iPhone, ni Android) : tout coût de frame cité est issu de sources ou de jugements marqués.
2. **Filtres SVG sur iOS** : documentés comme coûteux et capricieux ; WebKit change (PR `backdrop-filter: url()` en cours, notes de Safari 26) ; non retesté en 2026.
3. **Plancher de navigateurs du projet** (iOS minimal) : non lu ; il décide si `-webkit-backface-visibility`, `mask-image`, `content-visibility` (Safari 18) sont disponibles sans repli.
4. **Haptique iOS** : le contournement `switch` aurait été fermé par iOS 26.5 d'après une source tierce non vérifiée ; supposer qu'il n'y a **pas** de haptique sur iOS.
5. **Planche de frames des animations CSS/WAAPI sous horloge simulée** : comportement de `page.clock` sur la chronologie du document non vérifié ; utiliser `currentTime`/CDP `Animation.*`.
6. **Écouteurs passifs, `-webkit-touch-callout`, capture implicite des pointeurs tactiles** : non relus dans les sources primaires.
7. **Accessibilité** : le glissement impose un équivalent à un seul appui (WCAG 2.5.1 / 2.5.7) ; l'interface exacte reste à décider.
