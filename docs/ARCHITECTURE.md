# Architecture et conventions — le détail

Ce fichier est l'ancien `AGENTS.md` §6, déplacé tel quel (moins les numéros de version du store, qui
se contredisaient : la seule source est `migratePersisted`). `AGENTS.md` §6 garde les règles courtes ;
lire ce fichier avant de toucher la zone concernée.

Le projet est encore une **application Vite plate**. Le monorepo décrit dans `PROPOSITION.md` §6.1 est une cible, pas l'état actuel : ne pas restructurer sans décision.

## Où vit chaque couche, et pourquoi

Ce document ne recopie ni la liste des fichiers ni leur nombre : ils changent à chaque ticket, et une
copie prend vite du retard. Pour l'état réel, `ls <dossier>` ; pour les écrans, la liste est dans
`scripts/ci/detect-ui-pages.mjs`, et les routes sont déclarées dans `src/App.tsx`.

| Couche | Où elle vit | Pourquoi là |
|---|---|---|
| **Données des cartes** | `src/data/` : un fichier par faction, `index.ts` (`ALL_CARDS`, `CARD_BY_ID`), `actions.ts` (Collègues et Objets), `planque.ts` (le socle de faction), `factions.ts` (`FACTION_META`), `vocabulaire.ts`, `plan.ts` (la feuille de route, écrite à la main) et `plan-dev.ts` (généré) | un fait, un fichier : le moteur et l'interface lisent la même source |
| **Moteur de jeu** | `src/game/` : transitions (`engine.ts`), règles (`rules.ts`, `deck.ts`), chiffres (`curves.ts`), hasard seedé (`rng.ts`), Arrivages (`pack.ts`), simulateur et Direction (`simulation.ts`, `ia.ts`) | code pur, sans React ni DOM : une partie se rejoue à partir de sa graine |
| **Animation de Pression** | `src/animation/` | c'est de l'écran : le moteur n'en sait rien, et l'animation ne modifie aucun état de partie (D-098) |
| **Store** | `src/store/` (`useStore.ts`, `partie.ts`) | Zustand avec persistance ; la forme est versionnée par `migratePersisted`, seule source du numéro |
| **Écrans** | `src/pages/` et `src/components/` ; les routes sont dans `src/App.tsx` | une route, un écran ; les composants génériques de shadcn/ui vivent dans `components/ui/` seuls |
| **Styles** | `src/styles.css`, feuille unique ; le système visuel est dans `DESIGN.md` | une seule source de style, et le visuel a son document |
| **Illustrations** | `design/illustrations/` (le registre) et `src/art.ts` | une seule copie du registre (D-045) |
| **Base du mur** | `supabase/migrations/` (rejouées dans l'ordre par `pglite.ts`), et les gardes `supabase/*.test.ts` | la RLS se joue en PostgreSQL réel, sans Docker |
| **Poste de pilotage** | `tools/admin/` et `tools/serveurs/` | hors de l'application et hors du bundle : aucun secret ni client de base n'entre dans le jeu |
| **Scripts** | `scripts/`, **cinq dossiers par métier** (voir juste dessous) | la table des commandes est `docs/COMMANDES.md` |
| **Public et hébergement** | `public/` (icônes), `design/` (logo, vitrine), `vercel.json` (réécriture SPA, D-053) | ce que le navigateur reçoit tel quel |
| **Configuration de contribution** | `.github/` (CI, modèles de ticket et de PR), `CONTRIBUTING.md`, `CLAUDE.md` (qui n'importe que `AGENTS.md`), `.vscode/`, `.nvmrc` | le geste de contribution, et Node 24 comme version de la CI |
| **Documentation** | `docs/` ; `AGENTS.md` pour les règles d'agent | `AGENTS.md` §2 dit l'ordre d'autorité |

**`scripts/`, cinq dossiers par métier** (#481 à #485, 29/10/2026). Le dossier a vécu à **83 fichiers à plat** : on y range par **ce que le script fait**. Un test de script reste **à côté de son exécutable** ; les gardes de cohérence, qui n'ont pas d'exécutable à côté et lisent plusieurs modules, vivent dans `gardes/`.

| Dossier | Ce qu'il porte |
|---|---|
| `scripts/preuves/` | ce qui **mesure** : captures, films, parties jouées, parcours, pesages, traces, `status` |
| `scripts/generateurs/` | ce qui **écrit** : `plan-dev`, `notes-versions`, `index-decisions`, `problemes-connus`, `statut-mur`, `ouf` |
| `scripts/ci/` | la **chaîne** : chemins, état de `main`, format, durées, garde-fous, dispatch, isolation, worktree, détecteur d'UI, lots gflow |
| `scripts/ressources/` | ce qui **produit ou installe** ce que le jeu sert : icônes, sons, marques, import du mur, wizard d'illustration, installer, et deux wizards d'infra datés |
| `scripts/gardes/` | les **tests de cohérence** du dépôt, sans exécutable à côté |

Le cliquet est `scripts/gardes/rangement.test.ts` : un fichier posé à la racine de `scripts/`, un dossier vide ou un dossier inventé sans être nommé font échouer la suite.

- **Poste de pilotage local (`tools/admin/`, D-091, #184)** : un serveur `node:http` sur `127.0.0.1` (`npm run admin`), **hors de l'application et hors du bundle** — il n'importe rien de `src/` et `src/` ne l'importe pas. Il parle à la base par **deux rôles** (`postgres` pour les gestes, `lecteur` — `select` seul — pour le SQL libre en lecture), tient un **registre `admin.migrations` hors du schéma du jeu**, et son client (`pg`, devDependency) ne part **jamais** dans le bundle. Sa garde (`admin.test.ts`) n'atteint que l'API HTTP, sur un `pglite` injecté, sans réseau.
- **Tableau de bord des serveurs (`tools/serveurs/`, D-102, #227)** : un serveur `node:http` sur `127.0.0.1` (`npm run serveurs`, port **5180**), **hors de l'application et hors du bundle**. Il lit `ss -ltnp`, `/proc/<pid>/{cwd,cmdline,stat}` et `git worktree list --porcelain`, noue chaque port à son **dossier de travail** (donc à sa **branche réellement servie**, pas à celle du jour), et sait **lancer** ou **tuer** un serveur d'un chantier — en tuant l'**arbre** (`npm` → `sh` → `node`), jamais la seule enveloppe. Ses journaux vivent hors du dépôt (`~/.local/state/planquex-serveurs/`). Sa garde (`serveurs.test.ts`) n'exécute jamais `ss`, `git`, `npm` ni `kill` : le système est injecté, et les ports de test sont éphémères.
- **TypeScript strict**. Alias `@/` → `./src`, déclaré dans `tsconfig.json` et `vite.config.ts`.
- **UI en français**, identifiants de code en anglais. Ne pas dupliquer les textes de cartes hors de `src/data`.
- **Moteur** : code pur autant que possible, sans React ni DOM. `applyAction(state, action)` et fonctions de transition ; cloner avec `structuredClone`.
- **Déterminisme** : **fait** (ticket #29, 19/10/2026). Le hasard vient d'un générateur **seedé** — `src/game/rng.ts` (mulberry32) — et son état vit dans la partie (`BattleState.rng`), donc il se clone et se compare comme le reste. `createBattle(decks, seed)` utilise sa graine, le store est persisté avec migration (l'historique des paliers — `tutorielVu` de D-048, `cafeTypes` de #91, `combatDetaille` et `raccourcisCombat` de #189, renommages d'id de D-029/#87/D-095/D-096 — est celui de `migratePersisted`, `src/store/useStore.ts` ; la **forme courante** est dite à la ligne **Store** ci-dessous, seule source du numéro), et il ne reste **aucun appel à `Math.random()`** dans `src/game/` ni `src/store/`. **Journal d'actions et rejeu** : **fait** (ticket #83, 20/10/2026). `BattleState` porte sa **graine d'origine** (`seed`) et le journal des actions **appliquées** (`actionLog`) ; `applyAction` est le seul point qui journalise (une action refusée ne l'est pas), et `replayBattle(deck, deck, seed, actions, types de café)` reconstruit la partie — la cible de `PROPOSITION.md` §6.2 est donc atteinte : seedé **et journalisé**. Le **cinquième argument** (les types de café choisis, #91) est **facultatif** : omis, le rejeu retombe sur la dérivation d'avant. La **partie en cours** est désormais persistée elle aussi (#126) : le store range sa **graine**, ses deux Decks, ses types de café et son journal, et la rejoue à l'ouverture (`src/store/partie.ts`).
- **Store** : Zustand + `persist`, clé `bureau-des-planques-v1`. La forme persistée porte un numéro `version` dans `migratePersisted` (`src/store/useStore.ts`, **seule source du numéro** ; dernier palier : renommages D-095 et D-096), plus l'**export/import de sauvegarde** dans Réglages. Toute modification de forme doit être migrée ou versionnée.
- **Version (D-048, D-050, D-051, D-090)** : la règle complète vit dans **`docs/VERSIONS.md`** — à lire avant d'écrire un numéro quelque part. En bref : `package.json` porte `version` **et** `stage` (`alpha` | `beta` | `release`), injectés par `vite.config.ts`, lus par `src/version.ts` seul, affichés par `APP_LABEL` (« Alpha · » suivi du numéro) ; **l'étape porte la mineure** (alpha `0.1.x`, beta `0.2.x`, release `1.0.0`) et le **correctif** monte à chaque build donnée à quelqu'un ; jamais de suffixe `-alpha.N` ; le tag suit la version (`v<version>`) et la release porte le drapeau *pre-release*. **Et la note vit aussi dans le jeu** (D-090) : `src/data/versions.ts` est **pris aux releases GitHub** par `npm run notes:versions`, l'écran **`/feuille-de-route`** le lit (public, hors garde), et `src/data/versions.test.ts` refuse une version de `package.json` sans note. Garde : `src/version.test.ts`. **La feuille de route elle-même** (D-097 (3), #214) lit deux sources : `src/data/plan.ts`, écrit **à la main** (étape en cours, critères de sortie d'alpha de D-056, jalons de D-048, décidé pour plus tard de D-061, chacun citant sa décision) et `src/data/plan-dev.ts`, **généré** par `npm run plan:dev` depuis les issues `alpha` et `beta` ouvertes (`gh`, **aucun lien** dans le fichier : la page compose elle-même les liens que D-132 ouvre — releases et issues — à partir du numéro). Les modes parkés de D-019 ne s'y affichent **jamais**.
- **Données** : un fichier par faction, puis enregistrement dans `src/data/index.ts`. Ne pas oublier `ALL_CARDS`, `CARD_BY_ID` et les métadonnées. Les **cartes Action** (Collègues, Objets) vivent dans `src/data/actions.ts`. Le **socle de faction** vit dans `src/data/planque.ts` (`planqueBase`, `secretVariant`, `planquePalette`) et l'identité des factions dans `src/data/factions.ts` (`FACTION_META` : seule source de la Vulnérabilité et de la couleur unique dont le dégradé est dérivé) ; un fichier de faction ne déclare que ses cartes. Le **vocabulaire partagé** — le nom des deux camps (`CAMP_NAME`, `CAMP_SUJET`, D-108) et le libellé d'un café (`cafeLabel`) — vit dans `src/data/vocabulaire.ts`, un **module feuille** que le moteur peut importer (le store, lui, importe le moteur) ; le libellé d'une carte, lui, reste `kindLabel` de `src/data/index.ts`, qui lit les `*_META` de ce module. **Un fait, un fichier** (#248) : deux copies d'une étiquette ont déjà divergé — celle du plateau perdait la catégorie NEUF/MRO de D-027 — et `src/libelles.test.ts` refuse la deuxième.
- **Tests** : Vitest, fichiers `*.test.ts` / `*.spec.ts` à côté du code testé. Pas de test = pas de preuve.
- **Garde-fous** : une assertion qui garde une **règle** doit **pouvoir échouer** — une assertion qui passe quoi qu'il arrive ne garde rien, et trois cas ont été trouvés en une session (#101 le coût typé, #107 la rareté des variantes d'Action, #103 la table des écarts connus ; ticket #112). Deux moyens, et le second est celui qui manque le plus souvent : (1) un test « **le contrôle mord** » qui confronte le contrôle à un **cas fautif** ; (2) une entrée dans **`scripts/ci/garde-fous.mjs`** (table **courte, choisie, commentée** : chaque entrée cite son **ticket**, la **règle** qu'elle garde et les **tests ciblés**), mutée par `npm run garde-fous`, lancé par la CI. Ce qui peut être **désarmé** — la table elle-même — est surveillé par `scripts/ci/garde-fous.test.ts`, qui la compare à une liste attendue.
- **CI** : **`.github/workflows/ci.yml`**, trois jobs parallèles, à chaque push et pull request vers `main` — `npm run check`, `npm test`, `npm run garde-fous`, le détecteur d'UI (épinglé, #146), puis `npm run build` et le contrôle des artefacts, puis le contrôle visuel des écrans (#205, #234). Le détecteur ne doit pas se retélécharger (#146). **Les fichiers générés** (`src/data/versions.ts`, `src/data/plan-dev.ts`) ne sont **pas** vérifiés ici (D-113) : ils dépendent de l'état vivant de GitHub, et la CI des PR est tombée rouge trois fois le 26/10/2026 parce qu'une issue s'était fermée. **`.github/workflows/fichiers-generes.yml`** les vérifie sur un tag `v*` ou à la demande, avec `GH_TOKEN: ${{ github.token }}` (aucun secret ; `secrets.` reste interdit par `src/ci.test.ts`) ; il **échoue** si un fichier a divergé, ou si le jeton manque : un contrôle qui n'a pas tourné n'est pas un contrôle. On **vérifie**, on ne réécrit pas dans la CI : un fichier généré par elle ferait un commit fantôme.
- **PWA** : manifeste et Workbox dans `vite.config.ts`. `favicon.svg` est le monogramme « BP » de l'onglet ; l'icône d'application est l'illustration `public/icon-512.svg`, **rastérisée en PNG** (192, 512, 512 *maskable*) par `npm run icones` (`scripts/ressources/icones.mjs`, Chromium de `ms-playwright`). Sans PNG, Chromium/Brave n'installe qu'un raccourci avec son badge (D-054) ; garde : `scripts/ressources/icones.test.ts`. Le libellé sous l'icône (`short_name`) est **« Planquex »**, le nom du jeu (`name`) reste « Bureau des Planqués » (D-054).
- **Moteur — modules** : `engine.ts` (transitions), `deck.ts` (règles du Deck, partagées par le moteur et l'UI), `rules.ts` (drapeaux globaux, dont le mot-clé de D-004, **`STATUS_ORDER`**, l'ordre de résolution des conditions de §4, **et les chiffres du mode standard** — `HAND_LIMIT`, `POINTS_TO_WIN`, `BENCH_SIZE`, `STARTING_HAND`, `WEAKNESS_BONUS`, `SURCHARGE_DAMAGE`, `BURNOUT_DAMAGE` : un littéral recopié cinq fois finit par diverger, #248), `curves.ts` (le chiffré de `CARD-SPEC.md` §2 — dégâts par café et Seuil par stade/rareté — dont `cards.test.ts` et `pace.test.ts` sont les appelants), `rng.ts` (le hasard seedé, état porté par la partie), `pack.ts` (la composition d'un Arrivage, générateur en paramètre), `simulation.ts` (le simulateur headless), `mesure-direction.ts` et `mesure-archetypes.ts` (les **protocoles de mesure** publiés : D-134, rouges dans `docs/ia/`), `ia.ts` (la politique de la Direction — **trois niveaux** : niveau 1 scripté, niveau 2 la **recherche à deux coups** sur `evaluatePosition` (budget de nœuds **et** échéance murale, #172), et niveau 3 l'**expectiminimax** à profondeur 3 sur **K déterminisations** et tirages seedés (#94, `docs/ia/94-niveau3-expectiminimax.md`) — qui bat le niveau 2 de **55,94 %** au contrôle (seuil 55 %, ratio 1,15) **mais n'est branché nulle part** : le défaut reste le niveau 2 (D-084), et une branche par défaut attend une mesure seul et au calme. Les niveaux 2 et 3 vivent **hors** du moteur ; le niveau est un **paramètre** dont le défaut est **2** depuis D-084 (#172) — l'écran joue donc le niveau 2, et `nextAction` dans le simulateur reste au glouton ; employée par `nextAiAction` à l'écran **et** par `nextAction` dans le simulateur). Les règles de jeu ne vivent pas dans le store. **La scène de la Pression** vit à part, dans `src/animation/` (D-098) : `moteur.ts` (deux `canvas`, une horloge, particules, secousse, gel d'impact), `attaque.ts` (les **motifs de bureau**, un par attaque, et la cinématique réservée à la grosse Pression d'un COU, 3 étoiles ou COMEX) et `SceneAttaque.tsx` (le branchement dans `Battle`, muet sous « Mouvement réduit »). C'est de l'**écran** : le moteur de jeu n'en sait rien, et `src/animation/` ne modifie aucun état de partie.
- **CSS** : une seule feuille, `src/styles.css`, importée par `main.tsx`. Toute nouvelle page utilise les classes déjà définies plutôt que d'inventer un second système. Le **système visuel** — palette et jetons, gabarit de carte, cadre de rareté, badges de statut, mascotte, planches de style — vit dans **`DESIGN.md`** à la racine : c'est la source du visuel, comme `src/styles.css` l'est du style. **Style (D-035)** : **Tailwind v4** (mode CSS-first) est le **moteur de style**. `src/styles.css` **reste la feuille unique** : elle ouvre sur `@import "tailwindcss"` et un bloc `@theme inline` dont les valeurs **référencent les jetons de `:root`** (une seule source : `--color-bg` → `var(--bg)`, `--font-sans` → `var(--font-body)`, etc.), donc les utilitaires lisent `DESIGN.md` sans recopier un hex. Le `preflight` de Tailwind s'applique : nos règles maison le suivent et le corrigent ponctuellement (`h1,h2,h3` rétablit `font-weight: 700`). L'identité du jeu (carte, plateau, Collection) reste **maison**. **shadcn/ui** ne s'emploie que pour les **composants génériques** (dialogue, tiroir, onglet, formulaire, tableau), jamais pour l'identité ; ses **variables CSS sont mappées sur nos jetons** dans `:root` (`--background` → `var(--bg)`, `--primary` → `var(--accent)`, …) au lieu de ses valeurs « SaaS ». Config : `components.json`, `cn()` dans `src/lib/utils.ts`, composants dans `src/components/ui/`. Premier composant posé : `dialog` (règles des Conditions dans `Battle.tsx`). Le plugin `@tailwindcss/vite` est branché dans `vite.config.ts`.
- **Preuve de rendu** : un écran ne se déclare rendu que par capture ou inspection du navigateur, pas par la lecture du JSX. Voir §8.4.
- **Le comité (D-058, D-059, D-097)** : les retours des testeurs entrent **dans le jeu** — une **bulle** partout (sauf en combat) ouvre **le mur**, qui est une **page** (D-068) — l'écart à D-058 est assumé, un tableau ne tient pas dans un panneau. Le mur **lit et écrit la base** (#136, D-104) : la page lit `postits_avec_votes` par `src/lib/murBase.ts` et poste dans `postits` — `docs/comite.json` **n'est plus la source**, il reste le **contrat de données** et la trace de ce qui a été collecté avant (ses post-its sont importés en base par `supabase/imports/`). Sans configuration Supabase, le module rend `null` et la page retombe sur le fichier, en le disant : un mur n'est jamais un écran cassé à cause du réseau. Les deux familles de post-its (**IP** / **OUF**), les statuts, les champs du formulaire et le tri de fin de journée sont écrits dans **`docs/COMITE.md`**. Le mur complet (poster, voter, commenter) est la **première fonctionnalité Supabase**, et il vient **après le PvP**. Son socle est posé (#135) : `src/lib/supabase.ts` charge `@supabase/supabase-js` **à la demande** et reste **inerte** sans configuration — l'alpha fonctionne sans backend ; `supabase/mur.test.ts` applique la **migration réelle** (`supabase/migrations/`) dans **`@electric-sql/pglite`** (devDependency, PostgreSQL en WASM, RLS comprise), la machine n'ayant ni Docker ni CLI Supabase. **Le rangement aussi (#185, #186)** : sur la base, le mode de placement écrit la place au lâcher, et **la place passe par une fonction** (`deplacer_postit`, migration `0007`) et non par un `grant` de colonnes — une politique RLS ne distingue pas les colonnes, donc élargir l'`update` rendrait aussi `statut` à l'auteur, ce que D-059 refuse ; l'auteur range **ses** post-its, l'**administration** range et **retire** n'importe lequel à tout statut (D-092). Sur le fichier, le mode exporte le JSON à committer. Et un post-it neuf est posé là où il cache le moins de texte (`positionDepuisId(id, prises)`), pour que deux places tirées au hasard ne se recouvrent plus.
- **Illustrations** : le tuyau vit dans `design/illustrations/` (registre versionné + `README.md` + `PROMPTS-flow.md`), et **c'est la seule source** : depuis **D-045**, exécutée le 21/10/2026, Vite embarque les images dans le graphe de modules (`src/art.ts`, `import.meta.glob`, URL hachée dans `dist/assets/`) au lieu de les copier dans `public/`. Il n'y a donc plus de copie à maintenir, ni d'écart possible entre le registre et ce que l'écran sert ; la copie servie et son test #120 ont disparu, et `src/data/art.test.ts` reprend le rôle : fichier présent, nom = id de la carte de base, aucune orpheline, et **résolution par le glob de `src/art.ts`**. Le vocabulaire « les deux copies » a vécu — on dit **le registre**. La production passe par **`scripts/ressources/illustration-vague.sh`**, qui pilote **`gflow-cli`** (`uv tool install gflow-cli` ; `gflow auth login --browser chrome` une fois) : il génère, lit la **graine** dans le `--json` du CLI, range l'image **au registre** (une seule copie, D-045), consigne le registre et câble `art:` dans `src/data`. **Trois règles de ce wizard** : (1) il **sort en erreur** si `npm run check` ou les tests échouent — il n'invite jamais à commiter un état cassé, et dit comment revenir en arrière ; (2) il ne dit au registre que **ce qu'il a réellement fait** — les deux tableaux du README ne couvrent que la Planche 1, le **journal** est le registre vivant ; (3) la graine d'une image **déjà produite** (par le MCP gflow, qui ne rend pas de graine) se retrouve dans la base SQLite locale de gflow (`~/.gflow/gflow.db` ou `~/.local/share/gflow-cli/gflow.db`) ; à défaut, elle est consignée « inconnue », **jamais inventée**. Ses chemins sont **surchargeables par l'environnement** (`GFLOW_ILLUSTRATION_*` : `_SCRATCH`, `_REGISTRE`, `_SERVI`, `_README`, `_DONNEES`, `_PROMPTS`, `_DB`, `_CHECK_CMD`, `_TEST_CMD`) : c'est ce qui rend le wizard **testable de bout en bout**, dans un bac temporaire (`scripts/ressources/illustration-vague.test.ts`). **Dépendance signalée** (§1, règle 7) : un outil Python hors `node_modules`, alpha et reverse-engineered, qui pilote Google Flow sur un compte réel — l'automatisation relève des ToS de Google. **Et Pillow** (`python3 -c "import PIL"`) : le wizard convertit en webp les rendus de gflow, et son test fabrique de vraies images. Sans lui, **8 tests tombent** en `ModuleNotFoundError: No module named 'PIL'` — constaté le 21/10/2026, CI rouge pendant deux commits parce que la batterie locale passait, Pillow étant installé sur la machine de développement. La CI l'installe (`python3-pil`, `.github/workflows/ci.yml`) et le wizard le **vérifie avant de commencer**. **Le plan de la vague suivante — les 214 cartes qui n'ont ni sujet ni accent — est écrit dans `docs/SPEC-ILLUSTRATIONS.md`** (ticket **#121**) : douze décisions datées du 21/10/2026, dont deux engagent et sont actées (**D-045** la source unique, **D-046** les accents ré-dérivés de `FACTION_META.color`). **Le lot, et pas seulement la carte** : `scripts/ci/gflow-lot.sh` (26/10/2026) enchaîne plusieurs cartes en **une seule passe `gflow --prompts-file`** — une fenêtre, un projet — puis range au registre en appelant le wizard, seule source du prompt et du `--installe`.
